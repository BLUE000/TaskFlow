# TaskFlow 基本設計書 (Basic Design)

本システムは、PHP 8.1 / MySQL 8.0 で構成されたWebアプリケーションと、C++ / Qt 6 で構成されたデスクトップGUIアプリケーションが、データベースを共有・同期して動作するハイブリッド構成です。
データの暗号化および難読化には `TransCipher` ライブラリ（C++版/PHP版）を使用し、機密データを保護します。

---

## 1. システム構成とデータフロー

さくらインターネット（共有レンタルサーバー等）の本番環境における「MySQLデータベースの外部直接接続制限（ローカルPCからの直接ポート接続の遮断）」に対応するため、C++ デスクトップアプリは MySQL サーバーへ直接ポート接続せず、**PHPが提供する同期用Web API（HTTPS JSON通信）** を介してデータの同期処理を行います。

```mermaid
graph TD
    subgraph Web Server (さくらインターネット本番環境)
        PHP[PHP 8.1 API/Web]
        DB_Remote[(MySQL 8.0 Remote DB)]
        TransPHP[TransCipher PHP]
    end
    
    subgraph Local Client (C++ / Qt 6)
        QtGUI[Qt6 GUI App]
        DB_Local[(SQLite 3 Local DB)]
        TransCPP[TransCipher C++ DLL]
    end

    PHP <-->|PDO| DB_Remote
    PHP <-->|データ保護委譲| TransPHP
    
    QtGUI <-->|QSQLITE| DB_Local
    QtGUI <-->|DLL Link| TransCPP
    
    QtGUI <-->|HTTPS JSON API (Port 443)| PHP
```

* **常時オンライン (Web側)**: 一般閲覧者向けのカレンダー/ガントチャート表示、および管理者のWebログイン操作は、常にリモートDB（MySQL）の最新データを参照します。
* **オフライン対応 (C++デスクトップ側)**: インターネット未接続時でもローカルの SQLite 3 からデータを読み書き可能。オンライン復帰時に、Web API（HTTPS）経由でリモートDB（MySQL）とデータ同期を行います。
* **データ保護**: ローカルDB（SQLite）内のキャッシュおよびリモートDB（MySQL）内の機密データは、常に `TransCipher` で暗号化された状態で保存されます。
* **ビルドの簡素化メリット**: C++アプリからMySQL接続用ドライバの依存が消え、Qtの標準ネットワーク機能（`QNetworkAccessManager`）のみで完結するため、Windows, macOS, Linux でのビルド・配布が極めて容易になります。

## 2. データベース設計 (共通スキーマ)

MySQL 8.0 と SQLite 3 でデータ構造の整合性を保つため、共通のテーブルスキーマを定義します。
オフラインで生成されたデータとオンラインで生成されたデータが衝突しないように、すべての主キーに **UUID (VARCHAR(36))** を採用します。

## 3. SQLite 3 ローカル管理用メタテーブル

C++アプリ側のローカルDB（SQLite）でのみ、最終同期のタイミングや状態を管理するために以下のメタテーブルを定義します。

### 3.1. `sync_metadata` テーブル

| カラム名 | データ型 | NULL | キー | 説明 |
| :--- | :--- | :---: | :---: | :--- |
| `key` | VARCHAR(50) | NO | PK | 設定キー (例: `last_synced_at`) |
| `value` | VARCHAR(100) | NO | - | 設定値 (例: 最終同期日時 "YYYY-MM-DD HH:MM:SS") |

* **同期の判定**: SQLite内のレコードのうち、`updated_at` が `sync_metadata` の `last_synced_at` よりも大きいレコードは、前回の同期以降にローカルで追加または編集（あるいは論理削除）された「未同期レコード」と判断します。

## 4. 同期プロトコルと競合解決

### 4.1. 双方向同期フロー
C++アプリがオンラインになり同期をトリガー（起動時または手動実行）した際、以下の手順で処理を行います。

```
[同期開始]
   │
   ├─① リモート(MySQL)から「最終同期日時(last_synced_at)」以降に更新されたレコードを全取得 (プル)
   │
   ├─② ローカル(SQLite)内の「最終同期日時」以降に更新されたレコードを抽出 (プッシュ対象)
   │
   ├─③ 競合(衝突)の判定
   │   │
   │   ├─◆ 競合なし (ローカルのみ更新、またはリモートのみ更新)
   │   │   └─ 自動的にマージ (リモート更新をローカルに上書き、またはローカル更新をリモートに送信)
   │   │
   │   └─◆ 競合あり (同じUUIDのレコードが、ローカルとリモートの双方で last_synced_at 以降に更新されている場合)
   │       └─ 該当レコードを一時保留し、「競合解決ダイアログ」を表示
   │
   ├─④ ユーザーによる手動競合解決
   │   └─ 「ローカル側を採用」「Web(リモート)側を採用」「その場で再編集」を選択
   │
   ├─⑤ すべてのデータ書き込み（リモート・ローカルの更新）
   │
   └─⑥ ローカルの `last_synced_at` を現在のサーバー時刻に更新
[同期完了]
```

### 4.2. 競合（衝突）の判定基準
ローカルの最終同期時刻を $T_{sync}$ とします。同一UUIDのレコードにおいて、以下の両方が成立した場合に **「競合（衝突）」** と判定します。
* ローカルレコードの最終更新時刻 $L_{up} > T_{sync}$
* リモートレコードの最終更新時刻 $R_{up} > T_{sync}$

競合が検出されたレコードは、ユーザーが解決するまで同期処理を一時サスペンド（またはそのデータのみをスキップして競合解決を促すダイアログを表示）します。

## 5. データ保護設計 (TransCipher の適用)

### 5.1. 暗号化対象フィールド
* `schedules.title` (予定タイトル)
* `schedules.description` (予定詳細)
* `webhooks.url` (Discord Webhook URL)

### 5.2. 暗号化・復号用共通インターフェース設計
アプリケーションコードが `TransCipher` の内部仕様（バージョンごとのヘッダーサイズの差分など）に依存しないよう、またDB保存時のテキスト処理を共通化するために、暗号化・復号処理をラップする **`CryptoUtil`** インターフェースを定義します。

* **データの永続化形式**: `TransCipher` の出力はバイナリ形式（Version 2 は 64バイトのヘッダーを含みます。以前のVersion 1のヘッダー仕様等との差分があります）です。データベースの `TEXT` カラムに安全に保存するため、暗号化後のバイナリデータを **Base64エンコード** した文字列として格納します。復号時はBase64デコードしてから復号関数へ渡します。
* **メリット**: アプリケーションロジックはヘッダーサイズやバイナリ変換を意識することなく、透過的に「文字列の暗号化・復号」を行えます。また、将来的な `TransCipher` のバージョンアップ時もこのラッパー層の修正のみで対応可能です。

#### C++ 側呼び出し I/F (`CryptoUtil` クラス)
`Qt 6` 環境で、`QString` と `QByteArray` の変換および `TransCipher` の呼び出しを抽象化します。

```cpp
class CryptoUtil {
public:
    // 秘密鍵を設定して初期化
    static void init(const QString& secretKey);

    // テキストを暗号化してBase64文字列で返す
    static QString encrypt(const QString& plainText);

    // Base64暗号化文字列を復号して平文テキストで返す
    static QString decrypt(const QString& cipherTextBase64);
};
```
※ 内部実装では `CipherEngine::encrypt(data, key, AesMode::Mandatory)` と `CipherEngine::decrypt(data, key)` を呼び出し、結果オブジェクト（`CipherResult`）を適切にハンドリングします。

#### PHP 側呼び出し I/F (`CryptoUtil` クラス)
PHP環境において、APIサーバー接続設定と `TransCipher` 呼び出しを抽象化します。

```php
class CryptoUtil {
    // 秘密鍵とAPI接続用の初期設定
    public static function init(string $secretKey, string $apiToken = null, string $apiUrl = null): void;

    // テキストを暗号化してBase64文字列で返す
    public static function encrypt(string $plainText): ?string;

    // Base64暗号化文字列を復号して平文テキストで返す
    public static function decrypt(string $cipherTextBase64): ?string;
}
```
※ 内部実装では `CipherEngine::configure` による接続情報設定と、`CipherEngine::encrypt($data, $key, RecipeManager::MODE_MANDATORY, "2.0")` の呼び出しを行います。

## 6. 画面・UI構成案

### 6.1. Web表示側（PHP + HTML/CSS/JS） - 一般閲覧・簡易管理
* **カレンダー表示（月/週）**: 祝日CSV情報とともに表示。時間枠ごとのタスク所要時間が限界値（`limit_hours`）を超えた場合、カレンダー上の時間枠が警告色でハイライトされます。
  * **開始曜日の設定**: 月間カレンダーおよび週間スケジュールの開始曜日は「日曜日」とします（左端が日曜日、右端が土曜日）。
  * **非ログイン時**: 公開設定された予定のみを表示。
  * **ヘッダーの簡素化**: タイトルロゴ（TaskFlow）および「ハイブリッドスケジュール...」等の不要なシステム記述を非表示にし、一般閲覧者にとって直感的なナビゲーションとログインボタン等のみのシンプルなヘッダーとします。
  * **フッターとコピーライト**: カレンダー下部にフッターを配置し、コピーライトおよび主要な技術ライブラリ（TaskFlow, TransCipher, Qt 6, PHP 8.1, MySQL, SQLite 3）のクレジットを明記します。
  * **管理者ログイン時**: 非公開予定も鍵マーク（🔒）付き、かつ半透明破線のスタイルで表示。
  * **ログイン・ログアウト**: 画面右上から管理者ログイン（パスワード入力用のグラスモルフィズム風モーダル表示）およびログアウト操作が可能。
* **ガントチャート表示**: 期間予定・タスクの進行状況をタイムライン表示。非ログイン時は公開データのみ、ログイン時は非公開データも専用スタイルで表示。
* **カテゴリフィルター**: 存在するカテゴリからバッジ（チップ）を動的生成し、複数選択でのリアルタイムフィルタリングに対応。URLパラメータ（`?categories=xxx,yyy`）と連動し、アクセス時の自動絞り込みや、選択時のアドレスバーURL自動追従（replaceState）をサポート。
* **管理者用ダッシュボード（ログイン要）**: 簡易CRUD（予定の追加・編集）、一括公開/非公開切り替え、時間枠設定、Discord Webhook設定、および管理者ログインパスワード変更機能。

### 6.2. デスクトップアプリ側（C++ / Qt 6） - 管理者操作特化
* **メイン画面**: 予定の追加・編集・削除、およびカレンダー表示。
* **同期ステータス ＆ 競合解決画面**:
  * 同期進行インジケータ、オンライン/オフライン切り替え。
  * **競合解決ダイアログ**: 同一データで更新の衝突があった際、左右に「ローカルの更新内容」「Web(サーバー)側の更新内容」を配置して比較し、どちらを優先するかをユーザーが選択・マージできる専用インターフェース。

### 6.3. UI/UX 設計方針：シームレスな予定登録フロー
予定の登録手順が、その予定の「種類（簡易、期間、タスク）」によって別々のフォームに分岐したり、煩雑な操作ステップを強いることを排除し、以下のようなシームレスかつシンプルな予定登録フローを採用します。
* **統一された基本登録フォーム**:
  * 予定の追加UIは、基本的には「予定のタイトル」を入力するだけの極めてシンプルなインターフェースとします。
  * 「買い物や通院のような特定日固定の簡易予定」か、「数日間にわたる期間予定」か、「進捗・重みのある個人タスク」かという違いは、登録そのものには影響せず、すべて同じ基本操作で登録できます。
* **追加設定（メタデータ）による状態変化**:
  * タイトルのみを入力して保存した場合は、デフォルトで「簡易予定（イベント）」として登録されます。
  * 必要に応じて、後から（あるいは同一フォームのオプション展開で）「開始・終了日時」を設定すれば、自動的にカレンダーやガントチャート上に幅を持つ「期間予定」へ変化します。
  * 「進捗ステータス」や「重み（所要時間）」を設定すれば、自動的に「個人タスク」にアップグレードされ、時間枠負荷の集計対象や進捗管理の対象となります。

## 7. モジュール分割・独立設計原則

機能の追加・変更・削除を安全かつ容易に行うため、本システムはPHP（Web側）およびC++（デスクトップ側）の双方で、強結合を避けた**「疎結合・高内聚（高コヒージョン）なモジュール分割」**を徹底します。

### 7.1. PHP (Web側) のモジュール分割方針
各機能をクラスやネームスペースによって物理的・論理的に独立させます。

1. **データアクセス層 (Repository)**:
   * DB（MySQL）接続やSQLの発行は各リポジトリクラス（`ScheduleRepository`, `TimeSlotRepository` 等）に閉じ込め、ビジネスロジックやUI層からSQLを直接隠蔽します。
2. **暗号化層 (Security/Crypto)**:
   * `TransCipher` に依存する暗号化処理は `CryptoUtil` サービスに限定します。他のモジュールは `TransCipher` の存在を意識せず、`CryptoUtil::encrypt/decrypt` を呼ぶだけとします。
3. **通知モジュール (Notification)**:
   * Discord通知ロジックを `DiscordNotifier` としてクラス化し、予定登録ロジックから分離します。将来的に Slack やメールなどの通知先を追加する場合は、共通インターフェースを実装する形で容易に拡張可能です。
4. **祝日CSVパーサー (Holiday)**:
   * 祝日CSVの解析ロジックを `HolidayParser` として分離し、カレンダー描画ロジックから独立させます。

### 7.2. C++ (Qt 6) のモジュール分割方針
UIファイル（.ui）を用いた画面設計をベースにし、UI表示とビジネスロジック・ストレージ処理のモジュール間の結びつきを最小限にします。

1. **ドメインモデル (Models)**:
   * `Task`, `TimeSlot` 等のデータ型は純粋なドメイン知識のみを持ち、DB保存や暗号化のロジックは内包しません。
2. **ストレージ層 (Database)**:
   * SQLite接続とMySQL接続をそれぞれ `LocalDatabase` / `RemoteDatabase` クラスとして実装し、データのCRUD操作を抽象化します。
3. **同期エンジン (SyncEngine)**:
   * 同期の状態遷移、プッシュ/プルフロー、競合の検出は `SyncEngine` クラスが独立して制御します。UI（画面）から同期エンジンへの指示は同期/非同期の関数呼び出しで行い、同期エンジンからUI（上位）への応答や進捗、衝突検出の通知は **Qtのカスタムイベント（QEventの継承クラス）** を上位へポスト（投函）することで伝達し、疎結合を実現します。
4. **計算・スケジューリングエンジン (Scheduler)**:
   * 時間枠ごとの負荷計算や警告判定を行う `ScheduleCalculator` を分離します。UIのカレンダー描画ロジックやデータベース処理に依存せず、純粋なデータ入力に対して計算結果を返すモジュールとします。
5. **UI表示層 (Views)**:
   * GUI部品（ウィンドウ、ダイアログ等）はUI表示とユーザー入力の検知に徹し、Qt Designerの `.ui` ファイルを利用して定義します。UIは下位モジュールの関数を直接呼び出して処理を依頼し、モジュールからの応答はカスタムイベントハンドラ（`customEvent()`）をオーバーライドして受信・処理します。

## 8. セキュリティ設計 (Security Design)

Webアクセスによるシステム公開に伴い、不正アクセスや改ざん、情報の不正取得を防ぐために以下のセキュリティ対策を基本設計として義務付けます。

### 8.1. SQL インジェクション対策
* **PHP (Web側)**: SQLステートメントの構築において、文字列連結（`.` による結合）を用いた動的SQLの生成を原則禁止します。すべてのクエリで **PDOのプリペアドステートメント（Prepared Statements）** とプレースホルダーバインドを徹底し、入力値をエスケープします。
* **C++ (Qt 6側)**: `QSqlQuery` の実行において、文字列結合でのSQL作成を禁止し、`prepare()` メソッドおよび `addBindValue()` / `bindValue()` を使用してプレースホルダーによるパラメータバインドを行います。

### 8.2. XSS (クロスサイトスクリプティング) 対策
* **HTMLエスケープの徹底**: データベース（SQLite/MySQL）から取得したデータをHTML上に出力（描画）する際は、必ず **`htmlspecialchars($data, ENT_QUOTES, 'UTF-8')`** を適用してエスケープします。
* **対象データ**: 暗号化が解除された後のタイトルや詳細説明だけでなく、カテゴリ名やエラーメッセージなど、ブラウザに描画されるすべての動的コンテンツを対象とします。

### 8.3. CSRF (クロスサイトリクエストフォージェリ) 対策
* **ワンタイムトークンの検証**: 管理者のアクション（予定の追加・編集・一括公開切り替え、設定変更など）を処理するすべてのPOST/APIリクエストにおいて、ランダムに生成した **CSRFトークン** をセッションに格納し、リクエストパラメータのトークンと一致するかを厳密に検証します。一致しない場合はリクエストを破棄（403 Forbidden）します。

### 8.4. 認証とセッションの管理
* **セッションIDの再生成**: ログイン認証に成功した直後、**`session_regenerate_id(true)`** を実行してセッションIDを強制的に新しく再生成し、セッション固定化攻撃（Session Fixation）を防止します。
* **セッションクッキーの保護**: セッション開始時にクッキーのパラメータを設定し、スクリプトからの読み取りを禁止する `HttpOnly` 属性、およびHTTPS通信限定的 `Secure` 属性（本番運用時）を付与します。
* **パスワードのハッシュ化**: 管理者のログインパスワードはデータベースにプレンテキストで保存せず、PHPの `password_hash()` を用いてセキュアなハッシュ（BCRYPTなど）を施して保存します。
* **パスワードの安全な変更処理**:
  * 管理者画面からパスワードを変更する際、現在のパスワードの正当性を `password_verify` で確認した上で、新しいハッシュを作成します。
  * `config.php` の定数定義を安全に上書きするため、一時ファイル（`.tmp`）に更新内容を一度書き出し、成功した場合のみ `rename` を使ってアトミックに入れ替える安全なファイルI/Oを用いて定義ファイルを更新します。

### 8.5. その他の主要な脆弱性対策
以下の代表的な攻撃手法に対しても、設計レベルで防御措置を講じます。

* **OS コマンドインジェクションの排除**:
  * PHP側からシステムコマンド（`exec()`、`shell_exec()`等）を実行する仕組みを一切排除します（C++との連携をDB共有方式としたため、外部プロセスの動的起動そのものが不要になっています）。
* **ディレクトリトラバーサル (パスインジェクション) 対策**:
  * 祝日CSVのインポート処理等において、アップロードされた元のファイル名をそのままサーバーのファイル処理（`fopen`等）に使用せず、内部で生成した安全な一時ファイル名（例: `temporary_holiday.csv`）に固定化して処理します。これにより、ファイルパスに `../../` 等を混入させてサーバーの重要ファイルを読み書きする攻撃を防ぎます。
* **クリックジャッキング対策**:
  * 第三者のサイト上の `iframe` 内に本システムの画面が埋め込まれ、誤クリックを誘発されるのを防ぐため、HTTPレスポンスヘッダに `X-Frame-Options: SAMEORIGIN` を出力し、他ドメインからのフレーム内表示を禁止します。
* **詳細エラーメッセージの非表示 (情報漏洩対策)**:
  * データベース接続エラーやプログラム例外の発生時、生のSQLやファイルの絶対パス、スタックトレースなどを画面上（HTMLやAPIレスポンス）に直接出力することを禁止します。
  * 画面上には「システムエラーが発生しました」という抽象メッセージのみを返し、詳細なエラー情報はサーバー上のセキュアなエラーログファイルにのみ出力するよう例外ハンドリングを徹底します。
