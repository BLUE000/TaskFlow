# TaskFlow テスト仕様書 (Test Specification)

V字モデルに基づき、各設計フェーズに対応するテストケースを定義します。テスト実行時は、本仕様書に従って合否（Pass/Fail）を判定します。

---

## 1. 単体テスト仕様 (Unit Test)
**【対応設計: 詳細設計 (モジュール・クラス設計)】**
PHPおよびC++の暗号化/復号ラッパー `CryptoUtil` の独立した動作を検証します。

### 1.1. PHP 側 `CryptoUtil` 単体テスト
| テストID | テストケース名 | 入力データ/条件 | 期待される結果 (判定基準) |
| :--- | :--- | :--- | :--- |
| UT-PHP-01 | 空文字の暗号化 | `$plainText = ""` | 空文字 `""` が返却されること。 |
| UT-PHP-02 | 正常な暗号化・復号 | `$plainText = "Hello TaskFlow"` | 暗号化結果がBase64文字列であり、それを復号すると元の `"Hello TaskFlow"` に完全に一致すること。 |
| UT-PHP-03 | 空文字の復号 | `$cipherText = ""` | 空文字 `""` が返却されること。 |
| UT-PHP-04 | 不正なBase64の復号 | `$cipherText = "InvalidBase64#$@"` | `InvalidArgumentException` がスローされること。 |
| UT-PHP-05 | 異なる秘密鍵での復号 | 暗号化時キー: `key-A`<br>復号時キー: `key-B` | 復号処理時に `RuntimeException` がスローされること。 |
| UT-PHP-06 | 接続エラー時の挙動 | API URLに無効なホストを指定 | 接続エラーを検知し、`RuntimeException` がスローされること。 |

### 1.2. C++ 側 `CryptoUtil` 単体テスト (Qt6)
| テストID | テストケース名 | 入力データ/条件 | 期待される結果 (判定基準) |
| :--- | :--- | :--- | :--- |
| UT-CPP-01 | 未初期化時の暗号化 | 秘密鍵を設定せずに `encrypt("Test")` を実行 | 空文字 `""` が返却されること。 |
| UT-CPP-02 | 空文字の暗号化 | `plainText = ""` | 空文字 `""` が返却されること。 |
| UT-CPP-03 | 正常な暗号化・復号 | `plainText = "日本語テスト"` | 復号結果が元の `"日本語テスト"` に完全に一致すること（文字化けがないこと）。 |
| UT-CPP-04 | 異なる秘密鍵での復号 | 暗号化時キー: `key-A`<br>復号時キー: `key-B` | `std::runtime_error` がスローされること。 |
| UT-CPP-05 | 不正なBase64の復号 | `cipherText = "NotBase64!!!"` | デコードエラーを検知し、`std::runtime_error` がスローされること。 |

## 2. 結合テスト仕様 (Integration Test)
**【対応設計: 詳細設計 (同期・衝突検知ロジック)】**
ローカル（SQLite）とリモート（MySQL）のデータ同期、衝突検知、手動解決マージのデータ整合性を検証します。

### 2.1. 双方向同期テスト (正常系)
| テストID | テストケース名 | 初期状態 | 操作・手順 | 期待される結果 (判定基準) |
| :--- | :--- | :--- | :--- | :--- |
| IT-SYNC-01 | ローカル新規追加の同期 | 同期完了状態 ($T_{sync}$ 同期済) | 1. SQLiteに新規タスクA(UUID)を追加。<br>2. 同期を実行。 | MySQL上にタスクAが反映され、双方の `updated_at` が一致すること。 |
| IT-SYNC-02 | リモート新規追加の同期 | 同期完了状態 ($T_{sync}$ 同期済) | 1. MySQLに新規タスクB(UUID)を追加。<br>2. 同期を実行。 | SQLite上にタスクBが反映され、双方の `updated_at` が一致すること。 |
| IT-SYNC-03 | 論理削除の同期 | 同期完了状態 ($T_{sync}$ 同期済) | 1. SQLiteでタスクAを論理削除 (`is_deleted=1`)。<br>2. 同期を実行。 | MySQL上のタスクAも `is_deleted=1` に更新されること。 |

### 2.2. 衝突（競合）検知・解決テスト (異常系・解決系)
| テストID | テストケース名 | 初期状態 | 操作・手順 | 期待される結果 (判定基準) |
| :--- | :--- | :--- | :--- | :--- |
| IT-CONF-01 | 衝突（競合）の検知 | 同期完了状態 ($T_{sync}$ 同期済) | 1. SQLiteでタスクAのタイトルを "Local-Title" に変更。<br>2. MySQLでタスクAのタイトルを "Remote-Title" に変更。<br>3. 同期を実行。 | 同期エンジンが衝突を検知し、`conflictDetected` シグナルを発火して同期処理が一時サスペンドすること。 |
| IT-CONF-02 | 競合解決：ローカル優先 | IT-CONF-01 の衝突状態 | 1. 競合解決ダイアログで「ローカル優先」を選択して保存。 | 1. MySQL上のタイトルが "Local-Title" に上書きされること。<br>2. SQLiteとMySQL双方の `updated_at` が現在のサーバー時刻に更新され、同期完了となること。 |
| IT-CONF-03 | 競合解決：リモート優先 | IT-CONF-01 の衝突状態 | 1. 競合解決ダイアログで「リモート優先」を選択して保存。 | 1. SQLite上のタイトルが "Remote-Title" に上書きされること。<br>2. 双方の `updated_at` がリモートの更新日時に統一され、同期完了となること。 |
| IT-CONF-04 | 競合解決：手動マージ | IT-CONF-01 の衝突状態 | 1. 競合解決ダイアログのマージ欄に "Merged-Title" と入力し確定。 | 1. SQLiteとMySQLの双方が "Merged-Title" に更新されること。<br>2. `updated_at` が現在のサーバー時刻に更新され、同期完了となること。 |

## 3. システムテスト仕様 (System Test)
**【対応設計: 基本設計 (UI・DBスキーマ構成)】**
Web（閲覧・簡易管理）および C++アプリのユーザーシナリオに基づき、システム全体の機能を検証します。

### 3.1. 表示および負荷警告機能テスト
| テストID | テストケース名 | 前提データ条件 | 操作・手順 | 期待される結果 (判定基準) |
| :--- | :--- | :--- | :--- | :--- |
| ST-VIEW-01 | 一般閲覧画面の表示制限 | 予定A (`is_public=1`, `is_deleted=0`) <br>予定B (`is_public=0`, `is_deleted=0`) | 一般閲覧Web画面（カレンダー/ガントチャート）を表示する。 | 予定Aのみが表示され、予定B（非公開）が表示されないこと。 |
| ST-LOAD-01 | 時間枠負荷警告表示 | 時間枠A (`limit_hours = 3.0`) <br>タスクA (`weight = 2.0`, 時間枠A) <br>タスクB (`weight = 2.0`, 時間枠A) | WebおよびC++のカレンダー画面を表示する。 | タスクAとBの重み合計（4.0時間）が制限値（3.0時間）を超えるため、カレンダー上の当該日付の時間枠Aが警告ハイライトされること。 |
| ST-LOAD-02 | 完了タスクの負荷除外 | ST-LOAD-01 の状態 | 1. タスクBの進捗ステータスを `done` に変更。<br>2. カレンダーを表示する。 | 未完了のタスクA（2.0時間）のみが計算対象となり、合計値が制限時間内（3.0時間以下）となるため、警告ハイライトが消えること。 |

### 3.2. UI/UXシームレス予定登録テスト
| テストID | テストケース名 | 入力手順 | 期待される結果 (判定基準) |
| :--- | :--- | :--- | :--- |

| ST-REG-02 | 期間予定の自動判別 | タイトル「旅行」、開始「6/10 10:00」、終了「6/12 18:00」を入力して保存。 | DBに `type = 'period'` として保存され、カレンダー・ガントチャート上で3日間にわたるバーとして描画されること。 |
| ST-REG-03 | 個人タスクの自動判別 | タイトル「資料作成」、重み「2.5時間」、時間枠「午前枠」を設定して保存。 | DBに `type = 'task'` として保存され、ステータスが `todo`、重み `2.5`、時間枠IDが正しく格納されていること。 |

### 3.4. セキュリティテスト (Security Test)
| テストID | テストケース名 | 入力データ/条件 | 操作・手順 | 期待される結果 (判定基準) |
| :--- | :--- | :--- | :--- | :--- |
| ST-SEC-01 | SQLインジェクション防止 (Web) | タイトルに `' OR '1'='1` を入力 | Web管理画面から予定を登録・検索する。 | 構文エラーが起きず、暗号化されて正しく文字列 `' OR '1'='1` として保存・取得できること（他のレコードが漏洩・改ざんされないこと）。 |
| ST-SEC-02 | XSS防止 (Web) | タイトルに `<script>alert('XSS')</script>` を入力 | Webカレンダー画面を表示する。 | スクリプトが実行されず、文字列 `<script>alert('XSS')</script>` がそのままテキストとしてエスケープ表示（`htmlspecialchars`）されること。 |
| ST-SEC-03 | CSRF防止 (Web) | トークンなし、または無効なトークンを送信 | Web管理画面の予定保存APIに対してPOSTリクエストを送信する。 | リクエストが拒否され（403 Forbidden）、データベースが更新されないこと。 |
| ST-SEC-04 | 認証セッション保護 (Web) | ログイン成功時 | ログイン処理を実行する。 | セッションIDが変更（`session_regenerate_id`）され、古いセッションでのアクセスが不可能になること。 |
| ST-SEC-05 | SQLインジェクション防止 (C++) | タイトルに `'; DROP TABLE schedules; --` を入力 | C++アプリから予定を登録・検索する。 | テーブルが削除されず、文字列 `'; DROP TABLE schedules; --` として正しく SQLite / MySQL に保存・取得できること。 |
